# Working in `frontend/`

Vite + React + TypeScript app. `src/styles/README.md` is the canonical styling
guide; this file is the rules digest. Repo-wide rules and the closeout gate are
in `../CLAUDE.md`.

## Read before writing frontend code

- `../context/CODING_STANDARDS.md` (Frontend TypeScript) — feature-first
  organization, state ownership, module-size.
- For a screen: the relevant `../context/ui/pages/<page>.md` **plus**
  `../context/UI_UX.md` §0 (design intent) and §1 (common elements, incl. the
  DataTable model §1.7).
- For styling: `../context/DESIGN_SYSTEM.md` (tokens + blessed component
  inventory + doctrine — the source of truth), `src/styles/README.md` (the
  implementation how), and `../context/UI_UX.md` §0 (design intent).

## Visual pre-flight (any change a user can SEE)

This applies to a one-line CSS tweak as much as to a new screen — most
off-system UI arrives as "just a small fix". Before writing the rule, open
`../context/DESIGN_SYSTEM.md` and take the answer from it:

1. **Is there already a component for this?** § Component inventory. Reuse
   beats restyle.
2. **Is this a state?** hover / selected / armed / focus / disabled →
   § Interaction states. The ring colors, the washes, and the inset-outline
   mechanic are already decided; do not choose a color, and never draw an
   outset ring on a drawn object (it gets clipped).
3. **Is this a dialog?** § Modal contract. `ModalDialog` + `DialogActions`,
   footer is Cancel/primary only.
4. **Every value is a token** — color, space, radius, size, weight, z-index.
   No literal survives `pnpm run check:all`.

If nothing in the system fits, that is a design-system change: add the token or
the recipe to `styles/tokens.css` + `DESIGN_SYSTEM.md` in the same commit, so
the next screen inherits the decision instead of re-deciding it.

## Non-negotiables

- **`pnpm` only** (never npm/yarn). Keep supply-chain protections on (24h
  `minimumReleaseAge`, strict min-age, `blockExoticSubdeps`). Run
  `pnpm run format` after changes.
- **Display only** — all calculations and data manipulation live in the backend.
- **Plain CSS on the 3-tier token system** — no Tailwind, no shadcn/ui, no
  CSS-in-JS. Feature/shared CSS consumes `var(--token)`; raw hex literals are
  allowed only in the token-definition files (guard-enforced). Radix UI
  provides unstyled behavior primitives (modals, popovers).
- **Server state in TanStack Query**; tables on TanStack Table; client state in
  Zustand. Keep `App.tsx` and route files as composition surfaces, not feature
  logic. Feature-first folders under `src/features/`.
- **A mutation must refresh every query its write moved, not just the one it
  returns.** When a command's response slice does not carry a value some other
  query serves, that query keeps answering the pre-command value until its key
  changes — the control appears to ignore the user until they save. Two traps:
  key matching is element-wise, so `["…","thermal"]` does **not** cover
  `["…","thermal-standards", …]` (sibling, not child); and a test that asserts
  the request was *sent* does not assert the UI *changed* — assert the rendered
  value too.
- **DataTable basic affordances are parent-owned and uniform** (iron-law) — see
  `../context/UI_UX.md` §1.7 and
  `../context/technical-requirements/data-table.md`.

## Verifying in a browser

Read `../context/USING_A_WEB_BROWSER.md` before any browser work — the
Playwright/MCP browser tools are unreliable here. Run
`make agent-browser-ready` (starts/reuses :5173 + :8000 and seeds the
`AGENT-BROWSER` fixture, signed in as `codex@example.com`, never Ed —
single-active-session rule), then drive the app with
`frontend/scripts/agent-browser.mjs`. Full setup is in
`../context/ENVIRONMENT.md`. For Model Viewer issues, read
`../planning/archive/dated/2026-06-13/model-viewer/AGENT_BROWSER_NOTES.md`
first.

## Checks

`make frontend-dev-check` (fast, no DB) for CSS/layout/positioning; for logic,
`cd frontend && pnpm exec vitest run <test-file>`. The full gate before
reporting done is the closeout gate in `../CLAUDE.md`.

Vitest runs `.test.ts` files in the fast `node` environment (no DOM, no
`tests/setup.ts`) and `.test.tsx` files under jsdom (see `vite.config.ts`
`projects`). A `.test.ts` file that needs the DOM (e.g. `renderHook`) must
start with `// @vitest-environment jsdom` — without it the test fails with
`ReferenceError: document is not defined`.
